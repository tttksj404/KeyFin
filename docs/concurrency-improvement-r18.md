## MR 범위와 충돌 원인

충돌은 `FinanceEmailScreen.tsx`의 같은 본문 구간을 두 브랜치가 바꿔 발생했다. 이 브랜치의 실험용 `CoachingEntry` 삽입과 `develop`의 `ScreenHeader` 교체가 겹쳤다. 이전 HEAD `5254d02`와 target `89fc06a`의 `git merge-tree`는 해당 파일 한 곳에서 exit 1이었고, 복원 뒤에는 exit 0이었다. 병합 결과에서 겹쳤던 7개 파일의 mode·blob은 모두 `develop`과 일치했다. 팀원의 헤더나 백엔드 코드를 수정해 충돌을 해소하지 않았다.

검증 도중 target이 `69fdacb`로 갱신되어 다시 fetch했다. 복원 커밋 기준 병합은 여전히 exit 0이었으며 결과 tree는 `e66fbbc70462632efcffd9b459e479ea54a939cc`였다. 최종 커밋도 푸시 전에 최신 target과 다시 검사한다.

앱·Spring·원천 동기화 구현은 현재 MR에 포함하지 않는다. 관련 문서는 [AI API 인계 계약](app-integration.md)으로 바꿨으며 R15 등 과거 검증에는 제외 범위를 표시했다. R16 전용 문서와 원문 연결 문서는 별도 보관했다. 런타임은 `src/`·`scripts/`, 자동 검증은 `tests/`, 설명은 `docs/`, 원문 응답·로그·생성물은 Git 제외 `artifacts/` 또는 개인 보관소에 둔다.


## 온라인 배치 변경

- `gpu_execution.py`: 요청 수명과 연결 종료, CPU 토큰 검사 및 GPU 소비자 수명을 분리한다.
- `gpu_batching.py`: FIFO 대기열, 최대 8ms 수집, 같은 출력 상한, 최대 4건·패딩 포함 16,384토큰 한도로 생성한다.
- `gpu_runtime.py`: CPU 사전 검사용 tokenizer를 별도로 복사해 생성 중 토큰 검사를 허용한다. 각 입력의 실제 토큰 수와 생성 tokenizer 결과를 다시 대조한다.
- `gpu_worker.py`: 기본 `COACH_GPU_BATCH_SIZE=0`은 기존 순차 경로다. `1`~`4`로 켜는 후보는 [운영 설정](operations.md)의 제한을 적용한다.
- `gpu_contracts.py`: HTTP 요청·결과·backend 타입 9개를 공통으로 두어 실행기와 worker의 순환 import를 제거한다. 기존 `gpu_worker` 타입 재수출과 요청 JSON schema는 유지한다.

요청별 소유자·입력·결과는 합치지 않으며 교차 사용자 응답 캐시를 사용하지 않는다. 응답 개수가 맞지 않거나 모델 호출이 실패하면 해당 배치를 503으로 처리한다. 입력 초과 413과 지문 불일치 409를 보존한다. 클라이언트가 연결을 끊으면 대기 중인 생성은 취소하고 슬롯을 반환한다. 이미 시작한 GPU 호출은 끝까지 정리한 뒤 끊긴 요청의 결과만 버린다.

## 실험 기준

같은 단일 L40S·체크포인트 revision `1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0`·NF4·temperature 0·출력 상한 256토큰·호출당 30초·실제 토큰 사전 검사를 고정했다. 사용 직전 여유 메모리와 실행 프로세스를 확인하고, 임시 API·원장·토큰으로 분리했다. 기존 API·추론 프로세스는 교체하지 않았다.

365일의 합성 원장을 가진 별도 사용자·새 세션에서 다음 네 질문을 각각 네 번 실행했다. 이를 동시 1·2·4·8건 조건마다 반복하므로 **한 실행은 16건×4조건=64메시지**다. 동시에 시작한 묶음이 모두 끝난 뒤 다음 묶음을 시작한다. 지속 유입 부하나 운영 네트워크 시험은 아니다.

1. 예금과 적금이 어떻게 다른지 설명해줘.
2. 이번 달 외식에 얼마 썼어?
3. 이번 달 말까지 남을 현금을 예측해줘.
4. 이번 달 말까지 위험을 분석해줘.

시간은 서버 내부 loopback에서 메시지 POST를 시작해 전체 JSON을 받을 때까지다. 세션 생성·모델 적재·사전 스모크 시간은 표의 지연에서 제외한다. 중앙값은 관측 16개의 중간값이고 P95는 정렬한 표본의 `(n-1)×0.95` 위치를 선형 보간한 값이다. 표본 16개로 운영 P95나 통계적 우월성을 확정하지 않는다. 각 실행 전 8질문·73검사의 스모크를 별도로 수행하며 반복 검사를 새로운 독립 사례로 합산하지 않는다.

외식 정답은 합성 원거래의 3,000원·3건이다. 기준일 09/15 마감 이후 예측·위험의 기간은 09/16~09/30, 15일이다. FDT 수치와 기간의 불변성, 응답 출처, fallback, HTTP 상태를 함께 확인한다. 이때 미래 수치의 동일성은 실행 일관성이며 실제 미래를 맞혔다는 뜻이 아니다.

배치 2는 동시 8건에서 기존보다 느려 채택하지 않는다. 배치 4는 동시 8건의 P95를 줄였지만 동시 2·4건의 중앙값이 악화했다. `baseb`와 `batch4b` 비교에서 동시 8건 P95는 25.56초에서 23.16초로 9.37% 줄었지만 중앙값 차이는 0.89%다. 배치 4 / API 4는 API 8보다 관측 메모리를 804 MiB 적게 썼다. 따라서 **기본값 0을 유지하고 배치 4는 부하별 검증이 필요한 선택 설정으로 제공한다.** 모든 요청의 응답시간이 개선됐다고 판단하지 않는다.

최신 코드 `batch4d`와 `baseb`의 동시 8건 P95는 **25.56초 → 21.99초, 13.95% 감소**다. 반대로 중앙값은 **17.31초 → 17.73초, 2.46% 증가**했다. 오래 기다린 요청 구간의 관측 개선과 보통 요청의 개선을 구분한다. 이것은 앞선 기본값 유지 판단을 바꾸지 않는다.

기존 worker·API의 재측정이 `basea/baseb`이며 `batch2a/4a/4b`는 같은 API에 배치 후보 worker를 연결했다. 이후 연결 종료·타입 문제를 수정했고, 마지막 실행은 최신 API 패키지까지 함께 검증한다. 모델·질문·수치 계약은 같지만 후보 코드와 API 버전까지 모두 같은 단일 변수 실험은 아니다. 실행 순서를 무작위화하지 않았고 GPU 클록과 호스트의 모든 부하를 통제하지 않았다. 관측 차이를 운영 환경의 보장값이나 통계적으로 확정된 우월성으로 쓰지 않는다.

최신 API 준비 중 한 시도(`batch4c`)는 실행기의 `PYTHONPATH`가 기존 의존성 경로를 덮어써 `uvicorn`을 찾지 못했다. 요청을 보내기 전 0건에서 종료했고 임시 프로세스를 정리했다. 의존성 경로를 유지하도록 실행기를 수정했다. 이 준비 실패를 성공한 요청의 분모에 넣거나 모델 추론 오류로 바꾸어 집계하지 않는다.

## Jira 104: 예측과 예산의 기준 차이

미래 예측 오차는 전체 변동소비를 대상으로 하지만 월 예산 사용액은 `exclude_tag=NONE` 거래만 집계한다. 예산 제외 소비가 있으면 두 수치를 같은 대상으로 간주해 원인을 단정할 수 없다.

예를 들어 월초 소비 10,000원, 미래 예측 20,000원, 미래 실제 일반 소비 20,000원과 제외 소비 3,000원이라면 기존 오차는 -3,000원이다. 월 실제 소비는 33,000원이나 예산 사용액은 30,000원이다. 새 필드 `budget_excluded_consumption_krw`가 차액을 보존하고 `budget_comparison`이 비교 기준 및 불확정 진단을 반환한다. 기존 금액·오차·사용률 계산은 유지한다.

`observed_spending_basis=aligned`여도 인과관계를 입증한 것은 아니다. `causal_attribution_established=false`를 유지한다. 과거 저장 문서의 새 필드 부재는 `null`로 읽으며 현재 기준으로 소급 진단하지 않는다. 관측 정책 해시가 달라져 이전 정책 등록의 신규 채점은 차단되고 과거 결과 조회는 유지된다. 새 정책 평가는 새 등록으로 진행한다. 상세 계약은 [예측 검증](forecast-validation.md)에 있다.

## 검증과 남은 조건

전체 AI 테스트 **829 passed / 1 warning**을 확인했다. 경고는 기존 Starlette의 AnyIO `BlockingPortal` 사용 중단 예고다. 그 뒤 공통 타입만 분리한 최종 소스에서 GPU 관련 **23 passed**, 요청 클래스 9개 AST·Pydantic schema 7개 동등성, standalone import를 확인했다. 전체 Ruff와 서비스 타입 검사, 새 실행 모듈·공통 계약을 명시한 저장소의 `all` 타입 검사 모두 오류 0개다. 월별 관련 56건에는 제외 소비, 환불·취소, 예산 부재, 과거 저장 결과와 정책 해시 변경 검증이 포함된다.
