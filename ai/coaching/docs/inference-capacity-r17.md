# R17: GPU 한 장에서 코칭 추론과 동시 응답시간 확인

이 문서는 R17 실행 당시의 구현·설정 기록이다. 이후 동시 요청 배치 후보와 월별 진단 변경 및 채택 판단은 [R18 검증 기록](concurrency-improvement-r18.md)을 따른다.

2026-09-15에 기존 배포 모델과 설정을 복제한 격리 API·추론 프로세스로 직접 측정했다. **현재 모델은 L40S 한 장에서 실행된다. 이번 64건은 오류 없이 완료했지만, 동시 요청 8건에서 전체 답변의 중앙값이 16.64초로 증가했다.** 메모리 부족보다 요청 대기가 현재 시험의 주요 병목으로 보인다. 모델 가중치·서비스 동시성 설정을 변경하거나 새 구성을 운영에 배포한 실험은 아니다.

R16의 외부 거래 큐 개선은 현재 AI MR에서 제외된 과거 통합 실험이다. 그 실험은 LLM 답변 생성 시간을 측정하지 않았으며, 이번 R17에서 Python API와 GPU 추론 구간을 별도로 측정했다.

## 장치 확인과 시험 범위

팀 계정에서 L40S 4장이 보였지만 JupyterHub의 사용자 옵션·환경 변수에 장치 배정 정보가 없었다. 확인한 Hub 설정 파일도 없었다. 사용자가 지목한 물리 GPU 2번은 과거 실험의 선택과 일치했고, 실행 직전 compute 프로세스는 0개, 가용 메모리는 45,468 MiB였다. **이 정보로 학교의 공식 전용 배정을 확정할 수는 없다.** 여기서 검증한 것은 후보 장치 한 장에서의 실행 가능성과 해당 요청 부하의 동작이다.

임시 worker의 `CUDA_VISIBLE_DEVICES`와 허용 장치 목록을 동일한 GPU UUID 하나로 고정했다. 따라서 프로세스 내부의 논리 GPU 0은 그 후보 장치를 가리킨다. 기존 API·worker에 시험 추론을 보내지 않고 별도 포트·합성 사용자·SQLite를 사용했다. 시험 중 다른 compute 프로세스가 관측되면 이후 부하를 중단하도록 했다. 샘플링 사이의 짧은 외부 작업까지 배제하는 보장은 아니다.

종료 후 임시 프로세스가 모두 내려갔고, 후보 장치의 compute 프로세스 0개·가용 메모리 45,468 MiB를 다시 확인했다. 기존 API·worker의 프로세스 식별 정보와 health 응답도 전후 일치했다. 운영 서비스의 장치 설정은 변경하지 않았다.

임시 worker의 모델 health 메타데이터 전체가 원래 worker와 일치하는지 검사했다. runtime SHA-256은 `a73dc9f775ea8357b8ccf218794e6f6f6be92c16c0f9bff7a75664081902f31a`, config SHA-256은 `191e0af232104ed8b65258cf3fb2b842e288008baca7633c11b82a1ac7203aab`이다.

모델 준비 시간은 약 15.03초였다. 이미 파일이 있는 서버에서 프로세스를 시작해 health 준비를 확인한 시간이며, 모델 다운로드와 서버 최초 설치 시간은 포함하지 않는다.

## 어떻게 측정했는가

1. 현재 모델·프롬프트·설정을 유지하고 시험 절차와 질문을 먼저 저장했다.
2. 365일 합성 원장을 사용했다. 하루 1건, 7개 봉투를 순환하며 금액은 1,000~7,000원이다. 기준일은 2026-09-15 마감, 가정한 현금은 1,000,000원, 보호금은 100,000원, 봉투별 예산과 장부 잔액은 각각 100,000원이다. 실제 고객 자료가 아니다.
3. 기본 대화·후속 질문·소비 조회·개인 현황·예측·위험 분석 등을 포함한 기존 스모크의 8개 질문을 실행했다. 총 HTTP 요청 30회와 계약 검사 73건을 통과했으며, 모델 워밍업을 겸했다.
4. 아래 4개 질문을 각각 4회씩 실행했다. 동시성 1·2·4·8 각각 16건, 합계 64건이다. 동시에 실행되는 요청은 서로 다른 사용자와 새 세션을 사용했다. 각 묶음은 barrier에서 동시에 출발하고 완료 후 다음 묶음을 시작했다.
5. 서버 내부 loopback에서 메시지 HTTP 요청 직전부터 응답 JSON을 전부 읽을 때까지 측정했다. 라우팅·FDT 계산·설명 생성·그 사이의 대기가 포함된다. 사용자 등록·원장 입력·세션 생성·모델 준비는 이 시간에 포함하지 않는다.

| 질문 | 기대 처리 |
| --- | --- |
| 예금과 적금이 어떻게 다른지 설명해줘. | `finance_education` |
| 이번 달 외식에 얼마 썼어? | `spending_history` |
| 이번 달 말까지 남을 현금을 예측해줘. | `forecast` |
| 이번 달 말까지 위험을 분석해줘. | `risk` |

이는 단일 실행의 정해진 순서·반복 부하다. 무작위 운영 트래픽, 지속 도착하는 요청, 긴 대화 이력, 최대 입력 길이, 첫 토큰 지연, 외부 앱·프록시→Python API→GPU 전체 네트워크 지연은 측정하지 않았다. 결과를 본 뒤 모델을 조정하고 같은 자료를 최종 시험으로 재사용하지 않았다.

## 실제 응답시간

| 동시에 출발한 요청 | 건수 | 중앙값 | p95 | 최대 | HTTP 200 / 계약 통과 | 모델 오류 대체 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 16 | 3.80초 | 3.97초 | 3.97초 | 16/16 | 0 |
| 2 | 16 | 5.14초 | 7.12초 | 7.12초 | 16/16 | 0 |
| 4 | 16 | 8.98초 | 12.23초 | 12.24초 | 16/16 | 0 |
| 8 | 16 | 16.64초 | 24.33초 | 24.35초 | 16/16 | 0 |

중앙값은 정렬한 16개 시간의 가운데 두 값 평균이다. p95는 위치 `(16-1)×0.95`에서 선형 보간했다. 운영 요청의 95%가 항상 이 시간 안에 끝난다는 보장이 아니다. 표본이 작아 p95는 최대값에 가깝다. 사용자 수가 아니라 **동시에 시작한 메시지 수**를 의미한다.

질문별 중앙값은 다음과 같다. 각 칸은 4회 관측이며 요청 도착·대기 순서에 영향을 받는다.

| 동시 요청 | 금융 개념 | 확정 소비 조회 | 월말 예측 | 위험 분석 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 3.97초 | 1.25초 | 3.87초 | 3.75초 |
| 2 | 5.14초 | 2.03초 | 5.13초 | 7.11초 |
| 4 | 10.18초 | 1.29초 | 10.01초 | 11.02초 |
| 8 | 19.05초 | 7.17초 | 22.11초 | 14.40초 |

약 0.5초 간격의 GPU 조회 421회 중 메모리 사용 최대는 **18,639 MiB, 약 18.20 GiB**였다. 관측된 compute 프로세스는 최대 1개였다. 이는 이번 짧은 질문 부하에서 관측한 최고값이며, 최대 토큰 길이·학습·추가 모델 상주에 필요한 메모리 상한이 아니다.

## HTTP 성공 외에 무엇을 확인했는가

- 64건 모두 실제 LLM으로 경로를 선택했다. 각 응답의 routing 출처와 대체 사유를 검사했다.
- 금융 개념·예측·위험 분석 48건은 설명 출처가 `llm`이었다. 소비 조회 16건은 설계대로 `engine`이었다. 소비 조회는 라우팅에 GPU를 사용하고 확정 금액의 문장은 엔진에서 만든다.
- 최상위 설명과 routing에서 오류 대체 사유는 모두 없었다. 시험 메시지에 HTTP 413·429·timeout 응답은 없었다.
- 소비 조회 16건 모두 합성 원장의 외식 **3,000원·3건**, 조회 기간 **09/01~09/15**와 일치했다.
- 예측·위험 32건 모두 **09/15 마감 관측 → 09/16~09/30의 15일 예측**을 반환했다. 시작·종료·일수와 본문 표기를 추가 검증했다.
- 같은 입력의 수치 metrics는 동시성을 바꾸어도 동일했다. 이것은 실행 일관성 확인이며 실제 미래에 대한 정답 검증은 아니다.

예측 금액·위험 수치는 FDT가 계산한다. LLM 설명 출처가 `llm`이어도 응답 전체의 금융 숫자를 LLM이 산출했다는 의미는 아니다. 이 시험은 복잡한 금융 질문 전반의 추론 능력이나 고객 예측 정확도, 타 GPU·타 모델 대비 품질 동등성을 입증하지 않는다.

## 병목과 다음 개선 판단

R17 실행 당시 `gpu_worker.py`는 `CapacityLimiter(1)` 안에서 생성하며 실제 토큰 검사도 같은 limiter를 사용했다. `llm.py`의 모델 호출 동시성은 2였다. 이 실행은 여러 요청을 하나의 GPU 배치로 합쳐 생성하는 구조가 아니었다. 동시 요청이 많아질수록 GPU 작업과 API limiter 대기가 쌓였다. 세부 구간별 trace를 수집하지 않았으므로 지연 중 각 성분의 정확한 비율은 아직 모른다.

**한 장에서 구동 가능하지만 동시 8건을 빠르게 처리한다고 평가하기는 어렵다.** 관측된 p95가 24.33초이므로 운영 목표 응답시간과 도착률을 정한 뒤 그 조건으로 다시 검증해야 한다. 호출당 제한 시간 30초는 질문 전체의 30초 제한과 다르다. 한 질문이 라우팅·설명 등 여러 모델 호출을 할 수 있다.

후속 실험은 다음 순서가 적절하다.

1. 라우팅·토큰 검사·FDT·생성·대기 시간을 각각 기록해 병목 시간을 분리한다.
2. 토큰 검사와 생성의 잠금 분리 가능성을 검증한다. GPU 생성 충돌과 모델 접근 안전성을 검사한 뒤 동일 부하에서 비교한다.
3. 단일 GPU에서 요청을 묶는 추론 엔진 후보를 동일 모델·양자화·입출력 조건으로 비교한다. VRAM이 남는다는 이유만으로 현재 동시성 숫자만 높이지 않는다.
4. 긴 근거·긴 대화·지속 요청을 추가하고 반복 실행의 편차와 fallback을 함께 측정한다. 운영 네트워크와 공식 장치 배정 확인을 포함한다.

이번에는 이 변경을 적용하거나 속도 개선 달성으로 집계하지 않았다. Jira 110에는 단일 장치 응답 부하 검증의 근거로 연결하고, 104의 실제 고객 예측 정확도는 기존 미래 관측 검증 절차를 유지한다.

## 증거와 검증 상태

실험 전에 저장한 프로토콜과 실행 코드, 원문 응답·GPU 샘플·정리 결과는 로컬 실험 산출물로 보존했다. 인증·장치 식별 정보와 원문 응답은 저장소에 올리지 않는다. 저장소에는 본 보고서만 추가했다. 모델 실행·원장 생성·HTTP 검증 코드는 기존 코드이며, 실험을 실행한 개인 환경의 전송 도구는 런타임 의존성이 아니다.

| 증거 | SHA-256 |
| --- | --- |
| 고정 프로토콜 | `7bfa3863497f72589b3356b5009cd5440d5b22e1ebf8ceab2ce56ed41d9ece08` |
| 실행한 부하 시험 코드 | `3df7c1bc0a7b32bc5c71db465f7edef0f047b457da690e86fc4655a67c248501` |
| 원문 증거 ZIP | `59a7f2ca3dd9a355ad55b3d1054ec713fda05c29ce2d1a4cf429e80d5de5c331` |
| 원문 파일별 해시 목록 | `4400ba8ce2bdb428c3614f174ca94a70f32b5db5a620c34e9a844f0d990f55a2` |
| 집계 JSON | `462eb8ac724ac6793fc4eeb9a8f4305b877ce94c9767d16aecdef1a52ae957b6` |

원문 파일 8개의 해시를 확인한 후 제품 함수를 가져오지 않는 별도 검증 스크립트로 그룹별 건수·중앙값·p95·소비 금액·기간·출처·정리 상태를 다시 계산했다. 추가 로컬 토큰 한도·GPU 설정·LLM 회귀 시험은 **93/93 통과**했다. 이는 GPU 품질 시험과 별개다.

첫 준비 실행은 설정 메타데이터에 생략된 기본 `max_tokens`를 직접 읽어 `KeyError`가 발생했다. 질문 실행 전 0건에서 중단됐으며, 실제 `ModelConfig`로 기본값을 읽도록 시험 도구를 고친 다음 새 실행으로 위 64건을 측정했다. 첫 실행의 로그와 정상 정리 결과도 보존했다. 이 오류를 GPU 추론 실패나 최종 64건의 실패로 합치지 않았다.

현재 상태는 **직접 실행·자체 재검증 완료, 외부 감사 대기**다. 공식 장치 전용 배정, 운영 부하·네트워크, 실제 고객 예측 정확도는 미확인이다. 기존 MR 본문과 Jira 104·110의 진행 중 상태는 유지한다.
