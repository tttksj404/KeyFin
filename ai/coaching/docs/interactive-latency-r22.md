# R22 단일 사용자 대화 지연 분해와 경로 축소

## 결론

한 사용자가 질문 하나를 보낸 뒤 답을 기다리는 흐름에서 40초 이상 기다리는 상태는
허용 기준으로 삼을 수 없다. 다만 그 시간을 FDT 계산 시간이라고 부를 근거도 없다.
현재 코드의 FDT 어댑터만 분리한 측정에서 수치 예측과 위험 계산은 수십 밀리초 수준이었다.
긴 대기는 모델 호출, 모델 대기열, 연결, 저장, 또는 앱 호출 계층 중 어느 구간인지
실제 요청 단위로 분리해서 봐야 한다.

R22는 두 가지를 바꿨다.

1. 정확도를 해치지 않는 좁은 질문 문법에서만 불필요한 모델 분류를 없앴다.
2. 실제 HTTP 응답에 구간별 시간만 남기는 선택형 계측을 추가했다.

이 문서는 현재 앱의 실사용 지연을 측정한 보고서가 아니다. 개발 셸에는 현재 연결된
앱 API와 모델 설정이 없으므로, 이 코드만으로 특정 배포의 응답 시간을 주장하지 않는다.

## 과거 40초 수치의 의미

[R20 답변 내용과 동시 요청 지연](answer-quality-latency-r20.md#3-응답-시간)은 서로 다른
실행 후보와 동시 요청 수를 함께 비교했다. 그 표의 `40.04초`는 한 사용자 순차 요청이
아니라, 특정 후보에서 **동시 8건**을 보낸 32개 요청의 P95다. 모델 적재, 세션 생성,
준비 대화는 그 수치에서 제외돼 있다.

따라서 그 과거 수치를 현재 사용자가 겪는 한 번의 앱 대화나 FDT 시간으로 해석하면 안 된다.
반대로 현재 앱에서 40초를 관찰했다면, 그 요청의 모델 대기·생성·FDT·나머지 API 시간을
한 응답에서 분리해 원인을 확인해야 한다.

## 현재 FDT 단독 측정

현재 FDT 어댑터를 고정된 합성 90일 원장으로 워밍업 후 20회 실행했다. HTTP, 모델 추론,
모델 대기열, 저장소, 앱 네트워크는 포함하지 않았다.

| FDT 연산 | 중앙값 | P95 | 최대값 |
| --- | ---: | ---: | ---: |
| 검토 계산 | 8.205ms | 9.075ms | 9.290ms |
| 미래 수치 예측 | 20.008ms | 20.986ms | 21.313ms |
| 위험 수치 계산 | 23.453ms | 25.433ms | 26.350ms |

원시 측정은 Git에서 제외되는
`artifacts/latency-diagnosis-r22-fdt-component.json`에 보관하며 SHA-256은
`D8FD773737843E2DE9DA699A9A77BB8415B5369C4EC400898DE781C2E360EC11`이다.
이 결과는 FDT가 실사용 앱에서 항상 이 시간에 끝난다는 보장이 아니다. 다만 40초의
주요 원인을 이 CPU 내부 수치 연산 하나로 돌릴 수 없다는 분리 근거다.

같은 합성 흐름을 로컬 TCP API와 대체 모델로 끝까지 실행한 7개 대화성 요청은 중앙값
91.515ms, P95 104.905ms, 최대 105.508ms였다. 이 값에도 실제 모델 생성·대기열은 없으므로
배포 지연 지표로 사용하지 않는다. FDT·저장·HTTP 연결을 포함한 경로가 정상적으로
연결되는지만 확인하는 보조 근거다.

## 단일 사용자 경로

| 질문 종류 | 모델 분류 | FDT 수치 계산 | 최종 모델 작업 | 정확도 경계 |
| --- | ---: | ---: | ---: | --- |
| 승인된 한 개의 정확한 금융 정의 | 0회 | 없음 | 0회 | 고정 공식 근거 한 개만 그대로 반환 |
| 일반 금융 개념 질문 | 0회 | 없음 | 1회 | 모델은 승인된 근거 ID만 선택하며 새 수치·출처를 만들 수 없음 |
| 명확한 개인 잔액·소비 예측 또는 위험 질문 | 0회 | 있음 | 1회 | 좁은 문법은 모드만 고르고, 기간·수치·근거 검증은 기존 FDT 경로가 수행 |
| 모호한 질문, 개인 이력, 목표·가정·최적화, 시장 질문 | 기존대로 | 의도에 따라 | 기존대로 | 모델 라우팅과 기존 검증을 유지 |

예를 들어 `앞으로 7일 잔액 예측해줘`와 `이번 달 위험을 알려줘`는 이제 모델에게
"무슨 기능을 쓸지"를 먼저 묻지 않는다. FDT가 수치를 계산한 뒤, 최종 설명 생성 한 번만
기다린다. 반면 `예산 위험 알려줘` 같은 일반적인 문장은 빠른 경로에서 제외했다. 개인 FDT
질문인지 단정할 수 없으므로 기존 라우터가 판단한다.

모델 응답 상한도 작업별로 줄였다. 라우팅과 근거 선택은 최대 96 토큰, 일반 코칭 설명은
최대 160 토큰만 요청하며, 토큰 사전검사와 실제 생성이 같은 상한을 사용한다. 이는 출력
생성 시간을 줄이기 위한 제한이며, 답변의 수치·기간·행동 결정을 모델에 넘기지 않는다.

## 실제 앱에서 확인할 방법

진단할 요청에만 `X-Coaching-Trace: 1` 헤더를 넣으면 API는 `Server-Timing` 응답 헤더에
다음의 합계 시간만 반환한다.

| 항목 | 의미 |
| --- | --- |
| `api` | HTTP 요청 수신부터 응답 시작까지 전체 시간 |
| `fdt` | 결정론적 FDT 검토·수치 계산 시간 |
| `model` | 해당 요청의 모든 모델 호출 시간 |
| `limiter` | 서비스 내부 모델 호출 슬롯 대기 시간 |
| `tokenize` | 모델 서버의 입력 토큰 사전검사 시간 |
| `generation` | 모델 응답 왕복·본문 수신 시간 |

헤더에는 질문, 사용자 식별자, 금융 수치, 프롬프트, 모델 주소, 오류 본문을 넣지 않는다.
`api - fdt - model`이 크면 저장·외부 호출·앱 프록시 구간을 점검하고, `limiter`가 크면
동시 요청 설정을, `generation`이 크면 모델 입력 길이·출력 상한·서버 대기열을 점검한다.

실제 배포 검증은 같은 고정 질문 집합을 한 요청씩 순차 실행해 응답 전체와 위 헤더를
함께 저장해야 한다. 그 결과에서 일반 질문과 예측 질문 각각의 중앙값·P95, 오류·대체율,
근거·수치 계약 통과율을 같이 비교한다. 동시 8건 결과만으로 단일 사용자의 체감 시간을
판정하지 않는다.

## 이번 변경의 검증 범위

- 명확한 예측·위험 자연어 질문이 모델 라우팅을 건너뛰고도 최종 설명 한 번과 FDT 근거를
  유지하는 HTTP 회귀를 추가했다.
- 구조화된 목표·가정·최적화 요청은 빠른 경로로 잘못 전환되지 않는 회귀를 추가했다.
- 일반 금융 개념은 한 번의 근거 선택만 사용하며, Twin 없이도 응답하는 HTTP 회귀를 추가했다.
- 24개 고정 E2E 사례를 실제 TCP API로 실행해 실패 0건을 확인했다. 의도적으로 주입한
  한 건의 비정상 모델 응답을 포함한 모델 호출은 38회였고, 그중 성공 응답은 37회였다.
  두 자연어 빠른 경로와 두 명시 수치 경로는 모델 라우팅 호출 없이도 같은 수치·근거
  계약을 통과했다.
- 합성 사용자 한 명의 저장·결제·취소·대화·프로세스 재기동 흐름은 108/108 검사를 통과했다.
  이 흐름에서 네 개의 명확한 예측·위험 질문은 fallback 없는 결정론적 경로로 처리됐고,
  최종 설명과 수치 계약은 그대로 검증했다.

두 실행의 원시 결과는 Git에서 제외되는 `artifacts/`에 보관한다.

| 실행 | 보고서 SHA-256 | 해석 |
| --- | --- | --- |
| 24개 TCP E2E | `3D582A2059C8BFB58AD05972AF29B3936272458DF4F469DF8F443AF60810944D` | 합성 출력·바이트 토큰 대체물 기반의 경로·계약 검증 |
| 저장·재기동 흐름 | `7ACA679DA161F808308ABE969E624E36639DD911DE58994FD3D8191B7825DB60` | 합성 사용자 한 명의 HTTP·저장·재기동 회귀 |

현재 검증은 합성 입력과 대체 모델을 사용한 계약·경로 검증이다. 실제 사용자 데이터의
예측 정확도나 현재 배포의 지연을 의미하지 않는다. 실제 연결 환경에서 위 시간 헤더를
수집하고, 학습에 쓰지 않은 만기 거래 결과와 비교하기 전에는 그런 성능을 주장하지 않는다.
