# 금융 챗봇·예측 응답 검증 — 2026-09-14

**기존 API는 일반 금융 질문에 직접 답하지 못했습니다.** “복리가 뭐야?”도 FDT 검토와 확인 질문으로 처리했습니다. 일반 금융 개념·확정 소비 조회를 분리한 뒤 같은 8문항의 직접 응답은 3/8에서 8/8로 바뀌었습니다. 이는 개발 중 사용한 사례의 수정 전후 비교이며, 모든 금융 질문이나 실제 고객의 미래를 맞히는 정확도가 아닙니다.

현재 구현과 호출 예시는 [대화 API 계약](chat.md), 금융 수치 계산은 [AI·FDT 구조](architecture.md)에 있습니다. 이 변경은 기존 추론 모델 `latest27_nf4`를 그대로 쓰며, 모델 재학습이나 FDT 예측기 교체를 수행하지 않았습니다.

## 무엇을 어떻게 비교했나

- 수정 전: 기존 배포 API, 수정 후: 동일 모델 워커에 연결한 격리 API와 복제 DB. 모델 프로세스와 기존 API를 보존한 상태에서 비교했습니다.
- 같은 합성 원장과 `2026-09-03` 마감 상태를 사용했습니다. 8개 공통 문항은 각각 독립 세션에서 한 번씩 실행했습니다. 자연어 메시지에 `analysis`나 정답 라우팅을 강제로 넣지 않았습니다.
- 이후 거래 미연결·만기 표현·추가 개념·자료 부족·비금융을 포함한 총 20문항으로 확장했습니다. v1의 “이번 달 내 지출” 문법 누락과 비금융 질문의 잘못된 자료 안내를 고친 뒤 v2를 재평가했습니다. 따라서 최종 20문항은 숨겨진 최종 시험이 아닌 개발 회귀 집합입니다.
- 메시지 POST, 실제 GPU 추론, 답변 GET, 세션 GET을 기록했습니다. HTTP 200과 본문에 질문의 핵심이 있는지, 자료가 없을 때 적절히 안내했는지를 따로 검사했습니다.
- 개념 질문은 필요한 설명 요소·선택 근거 ID·출처를, 소비 조회는 기간·금액·범위 안내를, 예측은 기간·금액·위험 수치·조건부 추정 안내를 확인했습니다. 전문가 블라인드 평가나 자연어 의미 전반을 보증하는 평가기는 아닙니다.

## 통과 수치의 분모

확장 20문항의 HTTP·독립 세션·저장 GET 일치는 각각 20/20입니다. 내용 기준으로는 **답을 제공해야 하는 15문항 15/15**, **자료·범위 안내가 필요한 5문항 5/5**입니다. 20문항을 모두 “금융 지식을 답한 20건”으로 세지 않습니다.

자료·범위 5문항은 미지원 개념, 최신 최고 금리, 날씨, 연결되지 않은 개인 신용점수, 연결되지 않은 소비 조회입니다. 앞의 두 개는 `needs_source`, 날씨는 `out_of_scope`, 개인 자료 두 개는 `needs_data`였습니다. 문구 출처는 LLM 16건(자료 필요 선택 2건 포함), 원장 집계 1건, 정형 안내 3건입니다. 이 분포 역시 예측 정확도가 아닙니다.

일반 근거는 9종으로 제한됩니다. 유효한 근거 ID가 질문에 맞지 않아도 현재 스키마 검사만으로는 차단할 수 있습니다. 별도 검토에서 유효한 복리 ID를 잘못 주입하면 다른 금융 질문에도 `answered`가 될 수 있음을 확인했습니다. 이번 실제 GPU의 지정 문항은 통과했지만, 근거 검색 확장과 미사용 질문·복합 의도·전문가 채점이 남아 있습니다.

## 수치·배포·회귀 검증

공통 예측·위험 3문항의 수정 전후 `identity`, `period`, `numeric_request`, `numeric_result`는 모두 JSON 값이 정확히 같습니다. 원본 FDT 계산·수치 렌더러·날짜 계약은 유지됐습니다. 기준일 9/3은 관측 마감이고 7일은 9/4~9/10, 월말은 9/4~9/30입니다.

검증한 wheel의 서비스 Python 소스 43개가 로컬 소스와 바이트 단위로 같고, 격리 실행의 제품·엔진 파일 71개가 동결 매니페스트와 일치했습니다. 배포 전 DB 온라인 백업·무결성·스키마를 확인한 뒤 API만 교체했습니다. 배포 후 다음을 직접 확인했습니다.

- 기존 저장 차트 14개 GET 원문 바이트 일치.
- 명시적 7일 예측의 원본·분위수·본문·저장·이력 일치.
- 개념 단건 API와, 같은 세션의 개념 → 소비 → 월말 예측 → 위험 4회 연속 질문.
- 개념 단건과 연속 질문 4개 결과의 GET 원문 일치, 세션의 8개 메시지 일치.
- 모델 워커의 프로세스·상태 유지, DB 스키마 유지. 배포 실패 시 기존 API를 복구하도록 구성했고 이번 배포는 통과했습니다.

전체 `pytest`는 **586건 통과**, Ruff 통과, `basedpyright`는 오류·경고 0건입니다. 단위·통합 회귀에는 소비 이중 집계 방지, 미확정 제외, 윤년·월 경계, 소유격 문법, 무자료 안내, 인증 격리, 재전송·재시작, 예측 없는 질문의 기간 충돌, 라우터 타임아웃 원인 보존, 차트 구형 응답 역직렬화가 포함됩니다. 공개 측정기의 월말 기대값도 고정 27일에서 입력 기준일의 달력 계산으로 바꾸고, 별도 날짜 사례 6건을 추가했습니다. pytest에서 발생한 외부 Starlette/AnyIO 사용 중단 예정 경고 1건은 별도 의존성 갱신 대상입니다. 전체 테스트 로그 SHA-256은 `7c0d9a45774d62a9d32198c7e4ef3775ef1df61194cae73ddace34a1910304e5`입니다.

## 재현·원문 보관

실행 코드는 [대화 응답 측정기](../benchmarks/coaching/chat_response/README.md)에 둡니다. 원문 응답·로그·DB·wheel은 `artifacts/`에 보관하고 커밋하지 않습니다. API 실행 코드, 테스트 코드, 측정 코드, 생성된 결과를 분리합니다.

공개 `run`·`score` CLI도 동일 제품 소스와 기존 GPU 워커를 쓰는 격리 API에서 처음부터 재실행했습니다. 새 전용 소유자의 Twin 부재를 확인하고 12문항을 실행한 뒤, 거래를 연결하고 나머지 8문항을 실행했습니다. HTTP·저장·이력 20/20, 질문별 내용 계약 20/20, 모델 채택 16건·대체 실패 0건·정형 안내 3건·원장 답변 1건이었습니다. 메시지 응답 지연은 20건 중앙값 3.734초, 최소 1.516초, 최대 4.185초입니다. 같은 개발 문항의 재현이므로 앞의 v2와 합쳐 독립 40문항이나 새로운 일반화 성능으로 계산하지 않습니다. 공유 워커의 부하를 통제한 SLA 측정도 아닙니다.
