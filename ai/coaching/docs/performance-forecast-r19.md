# 응답 처리·예측 추가 실험 (R19)

2026-09-15. 현재 모델·팀 FDT를 기준으로 추론 실행 환경, 명시적 분석 요청의
오케스트레이션, 공개 원장의 예측 추가학습을 각각 분리해 비교했다.
서빙 지연 감소와 미래 예측 오차 감소는 서로 다른 결과다.

코드에 반영한 변경은 **명시적 예측·위험 요청의 중복 분류 제거**다. 같은 부하를
전후 두 번씩 비교해 동시 8건 P95가 각각 **41.31%, 19.49% 감소**했다.
GPU 예측 추가학습은 단순 기준모델을 넘지 못했으므로 팀 FDT를 교체하지 않는다.
[예측 추가학습·최종 평가](forecast-retraining-r19.md)에 실패 조건까지 기록했다.

## 무엇을 바꿨는가

`POST /v1/sessions/{session_id}/messages`가 `analysis.mode=forecast` 또는
`risk`를 명시하면 같은 의도를 GPU에 다시 분류시키지 않는다. 이 모드는
기존에도 자연어 분류보다 우선했으므로 요청 의미를 바꾸는 최적화가 아니다.
일반 질문은 기존 분류를 사용하고, FDT 수치 계산과 GPU 설명 생성은 유지한다.
기간 충돌, 수치 입력, 소유권, 재시도 검사는 기존 경계를 통과해야 한다.

```json
{"question":"이번 달 말까지 남을 현금을 예측해줘.","analysis":{"mode":"forecast","paths":100,"seed":42}}
```

위 예시는 명시적 분석 요청이다. 같은 질문만 보내는 일반 챗봇 요청의 속도가
이 변경만으로 빨라진다고 해석하면 안 된다. `routing.source=template`이고
`fallback_reason=null`인 확정 경로를 모델 실패로 세지 않도록 E2E 집계에도
`deterministic_routes`를 별도로 기록한다. 실제 시도한 분류·설명 호출만 모델
채택률과 대체율의 분모에 넣는다.

## 응답시간의 측정 기준

같은 체크포인트 `Qwen/Qwen3.8-27B`, revision
`1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0`, NF4, greedy 생성과 팀 FDT를 사용했다.
각 실행은 금융 개념·확정 소비 조회·월말 현금 예측·위험 분석 네 질문을
동시 1·2·4·8건 조건에서 각각 16건씩, 총 64건 반복한다.
매 실행 전 별도 8질문·73검사 스모크를 수행한다.

측정값은 loopback HTTP POST 시작부터 전체 JSON 수신까지다. 모델 적재,
사전 스모크와 세션 생성은 지연 표에서 제외한다. 중앙값은 표본의 중간값,
P95는 정렬한 16개 값의 `(n-1)×0.95` 위치를 선형 보간한다. 한 묶음이 끝나면
다음 묶음을 시작하므로 지속 유입 처리량이나 인터넷 응답시간 검증은 아니다.
64건은 네 합성 질문의 반복이며 64명의 독립 고객 평가가 아니다.

## 추론 실행 환경 비교

GPU 배치 4 / API 모델 호출 동시성 4를 고정했다. 모든 칸은 **중앙값 / P95, 초**다.

| 실행 | 동시 1건 | 동시 2건 | 동시 4건 | 동시 8건 | 최대 메모리 MiB |
| --- | --- | --- | --- | --- | ---: |
| Transformers 기준 A | 3.93 / 4.14 | 5.90 / 8.19 | 10.59 / 13.74 | 21.97 / 29.43 | 19,079 |
| FLA A | 3.66 / 3.89 | 5.57 / 7.78 | 11.63 / 13.53 | 19.96 / 27.55 | 19,063 |
| FLA B | 3.56 / 3.90 | 5.44 / 7.77 | 10.35 / 13.52 | 15.68 / 25.87 | 19,745 |
| Transformers 기준 B | 3.98 / 4.17 | 5.88 / 7.93 | 11.17 / 13.89 | 17.86 / 27.70 | 19,765 |
| vLLM A | 1.93 / 2.16 | 4.09 / 5.56 | 9.83 / 10.89 | 13.65 / 21.57 | 33,489 |
| vLLM B | 1.87 / 2.08 | 4.25 / 5.45 | 8.22 / 10.77 | 17.58 / 24.20 | 34,315 |

FLA는 별도 환경의 `fla-core==0.5.2`를 실제 CUDA worker에서 먼저 import하고,
chunk/recurrent 구현이 선택됐는지 기록했다. 양쪽 반복에서 동시 8건 P95를
20% 이상 줄인다는 사전 기준을 통과하지 못해 기본 설정으로 채택하지 않는다.
짝지은 FDT 수치 요청·계산 결과·기간은 32/32건씩 일치했다. 다른 문구는
위험 분석 말미의 지출 계획 질문이며 새로운 금액·확정 사실은 추가되지 않았다.

vLLM 환경은 `vllm==0.19.0`, `torch==2.10.0+cu128`,
`transformers==4.57.6`, `bitsandbytes==0.49.2`다. 기존 환경은
`torch==2.7.1+cu128`, `transformers==5.16.1`이다. 필수 라이브러리도 달라지므로
속도 차이를 vLLM 한 함수만의 효과로 분해할 수 없다. 같은 원본 가중치를
사용하되 NF4 패킹 차이는 실제 결과 대조로 검사한다.

vLLM의 단일 요청 중앙값은 약 절반으로 줄었지만, 동시 8건의 두 번째 P95는
24.20초로 두 기준 실행 대비 20% 개선 조건을 만족하지 못했다. 첫 번째 좋은
결과만 골라 채택하지 않으며, API 동시성 4 조합의 기본 적용을 보류한다.
두 반복 모두 64/64 응답 계약, 스모크 73검사, FDT 수치·기간 32/32 일치를
확인했다. C8 표본 수와 스케줄 변동을 고려해 두 반복을 그대로 공개한다.

입력 token IDs, 8,192 입력/1,536 출력 한도, FIFO·취소·인증·수치 검증은 유지했다.
vLLM의 prefix cache를 꺼 반복 질문 캐시의 이득을 배제했다. 내부 문맥은
9,728토큰, 최대 sequence 8, 메모리 비율 0.75, 단일 프로세스·텍스트 전용이다.
새 실행기의 hash를 별도로 기록하며 기존 런타임으로 표시하지 않는다.

실험 중 FLA import 순서 및 vLLM 장치 식별자 파싱 오류가 각각 한 번 발생했다.
두 시도 모두 본 부하 요청 0건에서 종료해 성능 표에서 제외하고 실패 기록을
보존했다. 장치 호환 처리는 실행자가 지정한 식별자를 현재 PCI 순서와 대조하고
실제 Torch 장치가 같은지 재확인하며, 임의 장치를 선택하지 않는다.

### vLLM의 API 동시성을 8로 바꾼 후속 비교

API 동시성 4의 실패를 확인한 뒤, 나머지는 유지하고 API 모델 호출 동시성만
8로 바꾸는 두 번의 후속 실행과 판정 기준을 먼저 고정했다. GPU 배치는 여전히
4이며 위의 명시적 경로 최적화가 없는 R18 API wheel로 일반 질문을 보냈다.

| 실행 | 동시 1건 | 동시 2건 | 동시 4건 | 동시 8건 | 최대 메모리 MiB |
| --- | --- | --- | --- | --- | ---: |
| vLLM / API 8 A | 1.92 / 2.04 | 4.27 / 5.55 | 9.22 / 10.86 | 11.50 / 15.88 | 34,653 |
| vLLM / API 8 B | 1.93 / 2.02 | 4.06 / 5.53 | 6.82 / 8.80 | 13.89 / 19.02 | 34,733 |

각 실행을 두 Transformers 기준 모두와 비교했을 때 동시 8건 P95 감소는
**31.36~46.03%**였다. 두 반복 모두 사전 20% 개선 기준과 단일 요청 비악화를
통과했다. 각각 64/64 계약·73 스모크 검사·32/32 수치 및 기간 일치를 확인했다.
본문은 A 48/64, B 49/64가 완전히 같았으며 변경은 위험 분석의 후속 질문 표현뿐이다.

따라서 이 부하의 **추가 검증 후보는 vLLM / API 동시성 8 / GPU 배치 4**다.
최대 메모리는 약 34GiB로 증가했다. 네 질문 반복에서 계약을 보존한 결과이므로
모든 금융 질문의 의미 정확도나 지속 유입 내구성까지 통과한 운영 기본값으로
표현하지 않는다. 명시적 경로 최적화와의 결합 효과도 이 표에서는 측정하지 않았다.

12개 완료 실행은 각각 64메시지이며 합계 768건이다. 같은 질문의 반복을
독립된 정확도 문제 768개로 세지 않는다. 모든 archive의 원문 hash와 종료·
기존 서비스 보존을 재검증한 집계 `serving-verdict.json` SHA-256은
`500e39f4c828c59cee6c7a0f725e880dba6d79077669ce48752ec8a67bdcd58b`다.

## 명시적 분석 요청의 중복 호출 제거

이 비교는 두 API 버전에 **동일한 구조화 요청**을 보내며, 이전 wheel→새 wheel→
새 wheel→이전 wheel 순서로 측정한다. 모델·worker·배치 4/API 동시성 4와
FDT·요청·원장은 같고, API의 명시적 경로 처리만 바뀐다. 예측·위험 질문에는
`analysis.mode`, `paths=100`, `seed=42`를 담고 금융 개념·소비 조회는 그대로 둔다.

| 실행 | 동시 1건 | 동시 2건 | 동시 4건 | 동시 8건 | 최대 메모리 MiB |
| --- | --- | --- | --- | --- | ---: |
| 이전 API A | 3.94 / 4.19 | 5.88 / 7.96 | 11.02 / 14.54 | 21.28 / 29.37 | 19,205 |
| 개선 API A | 2.26 / 4.09 | 4.75 / 5.87 | 7.14 / 9.73 | 12.28 / 17.24 | 19,847 |
| 개선 API B | 2.28 / 4.15 | 4.15 / 5.89 | 7.12 / 9.48 | 12.72 / 17.66 | 19,801 |
| 이전 API B | 3.88 / 4.11 | 5.98 / 8.17 | 11.16 / 13.66 | 14.97 / 21.93 | 19,745 |

실제 생성 계측에서 사전 스모크 호출을 따로 빼고 세면 64메시지의 모델 호출은
112회에서 80회로 28.57% 줄었다. HTTP 성공 건수를 모델 호출 횟수로 대신 세지
않는다. 이전 API 두 실행은 각각 125회−스모크 13회, 새 API 두 실행은 각각
93회−스모크 13회로 확인했다. 두 비교 모두 FDT 수치 요청·결과·기간 32/32건이
정확히 같았고, 네 실행 각각 64응답 계약과 스모크 73검사를 통과했다.
본문은 A 58/64, B 57/64가 완전히 같았고 차이는 위험 분석 말미의 지출 계획
질문 표현뿐이었다. 새로운 금액·확정 사실은 추가되지 않았다.

사전 기준인 각 비교의 동시 8건 P95 15% 이상 개선, 단일 요청 중앙값 5% 초과
악화 없음, 수치·기간 동일성을 모두 통과했다. P95는 A 29.37→17.24초,
B 21.93→17.66초이며, 단일 요청 중앙값은 각각 42.70%, 41.22% 줄었다.
기준 실행도 변동하므로 한 수치를 보장 지연이나 모든 요청의 개선율로 쓰지 않는다.
일반 질문만 보내는 부하 결과와도 분리해서 읽어야 한다.

## 코드 검증과 적용 범위

서비스 전체 회귀 **835건**, `src/tests/scripts/benchmarks` 전체 Ruff,
서비스 basedpyright가 통과했다. 연구 확장 스크립트 전체의 타입 통과를 뜻하지 않는다.
Starlette의 기존 BlockingPortal 별칭 deprecation 경고 1건은 남는다.
별도 리뷰에서 관련 64건과 잘못된 수치·기간·계산예산 12개 입력을 확인했으며
모두 거부 시 모델 호출·세션 변경이 없었다. 반복 실행은 독립 사례로 합산하지 않는다.

새 API wheel의 SHA-256은
`c3fa4efd9860f5cb56d86efb35a2f34ee5e84941a2e2039b2a25444cc2a3d082`다.
wheel 안의 `dialogue.py`가 검증한 원본과 같고 테스트·실험·결과 디렉터리가
포함되지 않는지 검사했다. 원문 응답·학습 가중치·로그·개인 서버 설정은
Git 제외 보관소에 두며, FE·BE·공유 코드는 수정하지 않는다.

재현 시 같은 요청·체크포인트·wheel·동시성·warmup·기간을 고정하고 실행마다
새 원장과 세션을 사용한다. 기존 추론·API 프로세스는 교체하지 않았으며,
각 실험 종료 후 임시 프로세스 종료와 기존 프로세스 보존을 확인한다.
새 API의 원격 wheel 실행은 격리 실험 배포이며 상시 서비스 교체 완료가 아니다.
